# اجرای مستقل، تنظیمات و تأیید استقرار

برای ارتقای این بسته از V3 به V4، [راهنمای مهاجرت کارگاه محتوا و درس بر اساس رشته](LMS-LEARNING-RELEASE.fa.md#ارتقا-و-بیلد) مرجع است. مراحل تاریخی زیر برای نصب این نسخه کافی نیستند.

## تنظیمات مورد نیاز

در Development از Secret Manager هر پروژه یا متغیر محیطی استفاده کنید. در Production از secret manager میزبان، مسیر پایدار و ACL محدود استفاده کنید. هیچ کدام از مقادیر واقعی را داخل سورس یا خروجی پشتیبانی نگذارید. الگوی تبدیل کلید: `:` → `__` در متغیر محیطی.

| میزبان | کلید | توضیح |
|---|---|---|
| API | `ConnectionStrings:DefaultConnection` | SQL Server خودتان؛ اتصال رمزدار با اعتماد صحیح به گواهی در Production. فایل Development نسخهٔ اصلی اتصال Windows بدون رمز را مثال زده؛ Linux یا SQL Auth نیاز به تنظیم خودش دارد. |
| API و Web | `Authentication:OpenIddict:ClientSecret` | یک secret قویِ یکسان برای کلاینت داخلی؛ مقدار در سورس نیست. |
| API | `Hosting:WebOrigin` | مبدأ بیرونی HTTPS بخش Web، با `/` در انتها مانند نشانی Development. Redirect URI موجود از همین ساخته می‌شود. |
| Web | `Authentication:OpenIddict:Authority` / `Api:BaseAddress` | مبدأ HTTPS معتبر API از دید مرورگر و Web؛ در توسعه پیش‌فرض ۷۴۴۳. اگر مسیر داخلی می‌دهید، issuer و دسترسی callback همچنان باید درست باشند. |
| API | `BootstrapAdmin:Enabled`, `FirstName`, `LastName`, `OrganizationalCode`, `NationalId`, `Email`, `Mobile`, `Password` تحت `BootstrapAdmin:` | نصب تازه: یک بار روشن. کد ملی واقعیِ مدیر با رقم کنترل درست و رمز موقت مطابق Identity؛ پس از ایجاد، خاموش و مقادیر حساس از تنظیمات اجرای عادی حذف شوند. ارتقا: حساب و رمز قبلی حفظ می‌شوند؛ نیازی به bootstrap نیست. |
| API | `PlatformSuperAdmin:UserName`، `DevelopmentUser:UserName` | فقط در صورت نیاز به اتصال به حساب قبلی تنظیم شوند. دومی صرفاً seed توسعهٔ قدیمی است و برای LMS لازم نیست. `Demo:Enabled` را خاموش نگه دارید. |
| API و Web | `Deployment:ApplicationName`, `Deployment:DataProtectionKeysPath`, `Certificates:DataProtection:Path`, `Certificates:DataProtection:Password` | برای هر میزبان پوشهٔ خصوصیِ پایدار و گواهی محافظت از DP لازم است. مسیرها و ACLها مجزا؛ پس از ارتقا کلیدهای قبلی را کنار نگذارید. |
| API | `Certificates:Signing:Path`/`:Password` و `Certificates:Encryption:Path`/`:Password` | گواهی‌های OpenIddict Production خارج از پروژه؛ رمز ذخیره نشده است. گواهی HTTP/TLS میزبان جداست. |
| API و Web | `Hosting:TrustedProxyIps:0` و … | فقط IPهای واقعی و دقیق پراکسی بلافصل همان فرایند. در API، IP Web BFF را تنها اگر اتصال داخلی اعتمادشده است اضافه کنید. خالی یعنی هیچ Forwarded Header از کاربر اعتماد نمی‌شود. |
| API | `Lms:PrivateFilesPath` | مسیر مطلق، پایدار، با ACL فقط فرایند API، خارج از WebRoot هر دو برنامه. فایل‌هایی که DB به آن‌ها ارجاع می‌دهد در پشتیبان بمانند. Development در `App_Data/Lms` محلی است. |
| API | `Lms:SmsProviders:<provider>:Endpoint` | فهرست مجاز درگاهٔ HTTPS توسط استقرار. سپس ادمین کل Provider و API Key را در پنل می‌دهد. کلید با DP محافظت می‌شود؛ پس از تغییر DP به وضعیت `KeyUnavailable` توجه کنید. |

قرارداد درگاه عملیاتی LMS: `POST` با `X-Api-Key` و JSON شامل `to`, `message`, `reference`. برای فروشنده‌ای که این قرارداد را ندارد، یک gateway مورداعتماد با نگاشت به قرارداد خودش قرار دهید. Endpoint دلخواه از UI پذیرفته نمی‌شود و redirect HTTP دنبال نمی‌شود. شمارهٔ تأییدنشده پیامک نمی‌گیرد. اگر درگاه در دسترس نباشد، برنامه ادعای تحویل نمی‌کند. وضعیت یادآوری درون‌سامانه‌ای مستقل است. کارگر هر چند دقیقه رویدادهای ۲۴ ساعت آینده را بررسی می‌کند؛ SLA ارسال فوری نیست.

## SQL Server تازه و ارتقا

برای بازطراحی تب‌های ارائه، نقطهٔ هدف `20261126093000_SeparateOfferingWorkspace` است. مسیر ارتقا از `AddLmsStudio` در [راهنمای بازطراحی](LMS-WORKSPACE.fa.md) آمده است. فرمان مربوط به `AddUniversityLms` در ادامه فقط نقطهٔ تاریخی پیش از Studio را نشان می‌دهد و برای نصب کامل نسخهٔ جدید کافی نیست.

1. SQL Server ایزوله برای تست؛ از نام DB جدا استفاده کنید. بازیابیِ نسخهٔ پشتیبان SQL و فضای فایل خصوصی را ابتدا امتحان کنید. زیرساخت عملیاتی تطابق schema و ابزار EF را بررسی کند.
2. دستورات Restore، Build و Test در README. برای تست‌های SQL، `RA_SQLSERVER_TEST_CONNECTION` و در صورت لزوم `REUSABLEACCESS_TEST_SQLSERVER` را به **نمونهٔ آزمایشی جداگانه** بدهید. فیکسچرها برای هر اجرای تازه DB با نام تصادفی `RA_LmsTest_...` ایجاد و حذف می‌کنند؛ اجازهٔ محدود و آزمایشی ایجاد DB نیاز است. هیچ تستی را با سرور Production اجرا نکنید. Skip محیطی قبولی نصب نیست.
3. نصب تازه: `database update` روی DB خالی با هویت استقرار؛ سپس API و Web را اجرا کنید و حساب اولیه را فقط یک مرتبه seed کنید. آزمایش ارتقا: روی کپی پایگاه مخزن مبنا، فهرست مهاجرت‌ها، الگوریتم Collation و معتبر/نرمال‌بودن شناسه‌های قبلی را بررسی کنید؛ در صورت وجود دادهٔ قدیمی نامعتبر یا نقش با کدهای رزروشدهٔ جدید، ابتدا در محیط آزمایشی بررسی انسانی. مهاجرت LMS دادهٔ تاریخیِ کاربران را بازنویسی نمی‌کند.
4. نقطهٔ ارتقا `20261103062810_CompleteAdminIdentity` → `20261121203400_AddUniversityLms` است. قبل از اجرا `has-pending-model-changes` باید عبور کند و خروجی SQL تولید شود:

```bash
 dotnet ef migrations script 20261103062810_CompleteAdminIdentity 20261121203400_AddUniversityLms --idempotent --project src/ReusableAccess.Infrastructure --startup-project src/ReusableAccess.Api --context ApplicationDbContext --configuration Release --no-build --output lms-upgrade.sql
```

   SQL را DBA بررسی و روی نسخهٔ کپی اجرا کند. از `EnsureCreated` روی پایگاه موجود استفاده نکنید. `Down` مخرب عمداً فعال نیست؛ در بازگشتِ استقرار از backup تأییدشده و بازپخش کنترل‌شدهٔ دادهٔ بعد از ارتقا استفاده کنید. هویت runtime نباید DDL معمولاً لازم داشته باشد. EF migration به صورت خودکار در startup اعمال نمی‌شود.

## انتشار API و Web

```bash
 dotnet publish src/ReusableAccess.Api -c Release -o publish/api
 dotnet publish src/ReusableAccess.Web -c Release -o publish/web
```

هر میزبان با تنظیمات خودش و ASP.NET Core Runtime 10 اجرا می‌شود. در Linux داده‌های `tzdata` و ICU و اعتماد CA لازم‌اند؛ در IIS با Hosting Bundle و تنظیمات binding و request filtering متناظر. برای Kestrel پشت پراکسی، HTTPS بیرونی، خط‌مشی `X-Forwarded-*` و IPهای اعتمادشده را تنظیم کنید؛ API را مستقیم از اینترنت یا مسیر دورزنندهٔ پراکسی باز نکنید. کلاینت Web از همان معماری موجود InteractiveServer/BFF استفاده می‌کند؛ session store پیش‌فرض حافظهٔ فرایند است. برای چند نمونه بدون affinity و ticket store مشترک، این بسته را «چندنودی آماده» فرض نکنید. `AllowedHosts` را برای استقرار واقعی محدود کنید.

## فایل و WAF

- مسیر مرحلهٔ اول: برنامه یک تلاش و GUID قبل از بدنه ثبت می‌کند. مسیر بدنه: `PUT /bff/lms/uploads/{TrackingId}` با CSRF و نوع `application/octet-stream`؛ Web جریان را به API منتقل می‌کند. هیچ base64 و هیچ دادهٔ فایل در SignalR/Blazor circuit نیست. download از `GET /bff/lms/files/{id}` بعد از بررسی دسترسی و وضعیت ثبت‌نام؛ Range برای نمایش ویدئو.
- برای مسیر PUT در همهٔ لایه‌های WAF/معکوس‌پراکسی/IIS، حد بدنه و timeout متناسب اعمال شود. عدد برنامه ۲۵۰٬۰۰۰٬۰۰۰ بایت برای بدنهٔ خام فایل است. در ingress خط‌مشی WAF را خاموش نکنید. تطابق اندازه، فرمت، سرعت و ظرفیت دیسک را با نمونهٔ اندازهٔ مرزیِ سالم، رد نوع/حجم، قطع معمولی و رد سیاست WAF در محیط آزمایشی جداگانه بررسی کنید.
- خطای قبل از رسیدن API هیچ حجم واقعی به برنامه نمی‌دهد. URL حاوی TrackingId اجازه می‌دهد ادمین کل نتیجهٔ پنل را با ثبت وقت UTC، status و کد رخداد لبه تطبیق دهد. لاگ شبکهٔ فروشنده هنوز به سامانه متصل نیست؛ از ثبت کوکی، query یا header حساس در لبه بپرهیزید. HTTP 413 یا اتمام‌نیافتن انتقال به‌تنهایی دلیل تأییدشدهٔ WAF نیست.
- محتوای فایل با پسوند و ساختار اولیه کنترل می‌شود، نه اسکن بدافزار صنعتی. قبل از محیط دانشگاه، فرایند AV/quarantine و خط‌مشی نگه‌داری فایل را با تیم امنیت تعیین کنید. برای ZIP/XML، قالب Excel بازخوانی محدود دارد. موقت‌های ورود Excel و تحویل‌هایی که به هیچ تلاش ثبت‌شده متصل نشده‌اند، سیاست جداگانهٔ پاک‌سازی پس از ۲۴ ساعت دارند؛ لاگ یک ماه است. خاموشی یا خطای سیستم فایل ممکن است orphan بسازد؛ با پشتیبان و مقایسهٔ کنترل‌شدهٔ GUIDها آشتی دهید، نه با حذف پوشهٔ عمومی.

## نتیجهٔ پذیرش مورد انتظار (وقتی اجرا شد)

- Build و تست کامل، سپس به‌طور خاص `WorkItemsConsoleReadContractTests`، `AcademicRulesTests` و `LmsPersistenceTests`. نصب خالی و ارتقا را مستقل اجرا کنید.
- یک حساب با پروفایل دانشجو و استاد؛ انتقال دانشجو، فعالیت تدریس را قطع نکند؛ آزمون race در ورود Excel و ثبت دستی.
- دسترسی خارج از دانشکده/رشته با URL مستقیم رد شود؛ ادمین آموزشی به نقش‌ها یا متن پیام خصوصی دسترسی نداشته باشد؛ پیش‌نمایش استاد ثبت پیشرفت نکند.
- نمایش قبل/بعد از آغاز مستقل درسک، بدون جلسه؛ مرز دقیق حذف‌واضافه؛ دو درخواست هم‌زمان خروج؛ حفظ شناسهٔ ثبت‌نام، تکلیف، فایل، نمره و پیشرفت بعد از هر دو خروج.
- تنظیم آزمون بدون افشای گزینهٔ درست در JSON دانشجو، ارسال مجدد و دیرهنگام، مخفی‌بودن پیش‌نویس، انتشار فقط برای دانشجوی مرتبط و read-only بعد از بسته‌شدن ترم.
- انتشار فصل دوم و ذخیرهٔ نسخهٔ خصوصی بدون اثر بر سوابق، گفتگوی ورودی و گفتگوی ارائه با دو حوزهٔ مجزا، و تقویم جلالی با رویداد خصوصی دریافت پاسخ؛ نبود پیامک نباید به‌عنوان موفقیت گزارش شود.
- آزمایش امنیتی/عملیاتی روی HTTPS و پراکسی واقعی: لاگ ورود موفق/ناموفق و قفل، بازیابی و تغییر رمز، دسترسی ردشده، تغییر نقش، فایل موفق/ناموفق و حجم مرزی. لاگ‌های یک‌ماهه پاک شوند ولی فایل‌ها و سوابق لینک‌دار باقی بمانند.
